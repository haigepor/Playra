# SDK 播放源分组与自动最高画质方案

日期：2026-10-14。当前代码基线 `a8fddbcb`。本轮为 L 级研究/设计：涉及统一来源契约、搜索跳转、SDK 解析与 Web/原生播放会话，尚未实施应用代码修改。

## 需求理解

用户希望先选择一个影片的 SDK 播放源，再由这个 SDK 自动选择当前影片/集数下画质最高且能够播放的线路；点击线路选择入口，可以切换该 SDK 的其他线路。当前 SDK 在产品上显示小写 `miomedia`，未来其他 SDK 与它并列。

数据层包含作品、提供方、提供方内作品引用、线路、剧集、清晰度；用户主要操作“播放源”和“播放线路”两层，清晰度默认自动，避免额外选择步骤。

```text
一部影片
  播放源：miomedia
    线路：自动（最高画质） / 高速线路 / 稳定线路 / ……
      当前集可选清晰度：由真实接口或媒体声明决定
  以后接入的 SDK：各自拥有线路、集数与清晰度
```

“所有线路”指该作品详情当前返回的全部合法线路，动态包含未来新增代码；不能把上一轮观察到的 7 种线路强行挂到每部影片上。没有资源的影片不能通过添加按钮变成有资源。

## 当前实现核对

| 层次 | 已有能力 | 与目标的差距 |
|---|---|---|
| 来源注册 | `ContentSearchProvider` 已有 `id/name/groups/search/lines/episodes/resolve`，`MioContentProvider.id` 为 `miomedia` | 可以复用来源注册，不必重建另一套 SDK 清单；显示名目前为 `MioMedia`，目标为 `miomedia`。 |
| 搜索聚合 | `ContentWork.hits` 已保存多个提供方的真实引用，并按身份/标题/分类/年份判定聚合 | 页面跳转仍针对 `MioContentProvider`/`MioVideo` 特判；不能靠新增 SDK 名称就获得通用播放页。 |
| 作品详情 | 从当前作品的 `player[]` 读取全部合法线路 | 页面直接平铺线路，缺少外层 SDK 播放源选择。 |
| 自动选线 | `MioPlaybackCoordinator.ranked()` 根据本平台成功记录和耗时排序，缺省沿用上游顺序 | 不是按画质排序；一次自动起播最多实际尝试 3 条，不代表全 SDK 只有三条。 |
| 清晰度 | Python 桥的 `play` 已接收可选 `quality`，SDK 有 `qualities` | Dart 的 `MioMediaService.play()` 没有传入画质；SDK 未指定时取 `qualities` 第一项，不保证最高。 |
| 解析多档候选 | SDK 的客户端解析支持多档结果和指定档位 | 当前解析最终只交付所选 URL，默认第一档；需要在选择阶段保留必要的候选/画质证据，而非过早丢掉。 |
| 手动换线 | 会取消旧请求并加载新线路的剧集目录 | 目前 `selectLine()` 不自动匹配当前集并开始播放，也未实现跨线路的进度交接。 |
| 播放器 | Android 影视复用原生播放器；Web 复用 media_kit 的 video 和 ArtPlayer 控件 | 新逻辑应只换媒体会话，保持同一个平台播放器实现。 |

源码位置：`lib/services/source/content_providers.dart`、`content_search.dart`、`miomedia/miomedia_service.dart`、`miomedia_playback_coordinator.dart`、`lib/presentation/modern/pages/content_search_screen.dart`、`miomedia/miomedia_detail_page.dart`、`tool/source_runtime/miomedia_adapter.py` 与私有输入的 `vendor/miomedia/playback.py`。

## 产品呈现与默认行为

沿用现有深色与淡紫色 token，不新增确认作品弹窗。

```text
播放源      [ miomedia ✓ ]
播放线路    自动 · 高速线路2    1080p  ›
选集        ……
```

上例“高速线路2 / 1080p”只是排版示例，不是宣称这条线路固定优于其他线路。应显示实际选中的名称、画质和状态。

点开“播放线路”使用同风格底部面板，包含“自动（最高画质）”与该作品的全部线路。每项可显示已知画质、当前选择、目录为空/超时/不支持等状态；未知画质显示“画质待确认”，不能伪装为 1080p。目录为空或没有对应当前集的线路保留状态与重试路径，不自动播放其他集。

- 当前只有 `miomedia`：进入播放页自动加载详情/目录并开始自动选线，不要求用户再点一次源或播放按钮。
- 用户主动选择 `miomedia`：立即在它内部运行自动最高画质策略，不能擅自换到另一个 SDK。
- 后续接入其他 SDK：按真实匹配的提供方并列展示，没有实现或没有匹配资源的 SDK 不放可点击占位按钮。
- 手动选择线路：以用户选择为优先，自动匹配当前集后直接解析/播放；不得随后被后台探测结果悄悄切回。选择失败时提供明确原因和“恢复自动”，不要静默改选。
- 自动播放已经开始后，其他探测迟到返回更高档位，不应突然打断播放；可以更新可选项，由用户切换，下一次自动选择再使用新证据。

## “最高清”的可验证定义

应定义为：**当前 SDK、同一影片版本、同一剧集、当前权限与设备支持范围内，在已取得画质证据的候选中，优先选择最高画质且能起播的线路。**

线路名称“蓝光超清+”“稳定线路”“高速线路”只是名称，不作为分辨率排序依据。4K/1080p 等可信分辨率可用于排序；“原画/超清”没有尺寸时不能直接视作最高档。

本轮对真实服务做了 4 次清晰度读取，均未进行播放换取：

| 作品/集数 | 线路 | 返回清晰度 |
|---|---|---|
| 唐探1900 / 第 1 项 | `ffm3u8` | `quality=1080p`、`label=超清` |
| 凡人修仙传 / 第 1 集 | `dym3u8` | 同上 |
| 凡人修仙传 / 第 1 集 | `ffm3u8` | 同上 |
| 凡人修仙传 / 第 1 集 | `sb` | 同上 |

这说明当前样本在 SDK 声明层面可能同为 1080p，不能仅凭这些字段分出真实最高码率或最佳片源。若解析结果提供可信的不同档位、HLS 主列表的分辨率/编码信息，可以继续补充；若没有，必须标记比较依据不足，不承诺“已验证全网最高画质”。

排序建议：先排除错片/错集、当前权限不可用及设备明确不支持的候选；再按有证据的画质从高到低；同画质按本平台真实起播成功与耗时排序。未知画质保持独立状态，不把它直接判定为低清。码率只能在可比的编码/版本等条件下作辅助，不把码率大小等同绝对画质。

SDK 声明画质和实际媒体核验结果应分开保存/显示。解析输出与声明不符时记录降级，不能把实际 720p 继续标成已核验 1080p。

## 自动选择与并发流程

1. 从已匹配的作品引用取得当前 SDK 的详情，按线路代码去重，读取该作品的动态线路集合。
2. 按当前集语义匹配各线路目录；电影不同版本、剧集季数、特辑和日期集不能按列表位置乱配。
3. 并发读取可匹配线路的目录/清晰度等元数据，独立超时、独立状态并复用有效缓存；建议并发上限先设 3，可配置，不用逐线路串行等待元数据。
4. 对当前可比较的候选按画质优先策略排序；元数据有整体截止预算，超时项显示“未确认”，不能说已比较全部线路。
5. 对最高优先候选执行播放换取/解析。换取可能消费凭证或一次性 nonce，不能为了测速无差别并发兑换所有线路，也不能把多个播放器同时启动。
6. 得到媒体后装入现有平台播放器，首帧/实际起播才确认成功。HTTP 成功、目录非空或拿到地址都不能单独当作播放通过。
7. 最高档失败时继续尝试同画质其他线路，再降到下一档；若总预算耗尽，展示尚未尝试数量与手动选择，不把预算耗尽说成全部线路失效。

“全线路接入”不要求对全部线路同时启动视频。并发适合目录和画质比较，实际播放会话只有一个。确定可用最高候选时不必等待无关慢请求；仍可能影响最高档判断的请求必须等到完成或明确超时。

## 多 SDK 的统一接口与状态

复用 `ContentSearchProvider` 的已有适配模式，逐步补充可选画质能力和统一播放会话。不要让公共页面继续直接识别某个 SDK 的模型类型，也不要求未来 SDK 拷贝一套播放页。

建议的职责与数据（均为拟议，尚未实现）：

| 结构/职责 | 核心信息 |
|---|---|
| 提供方注册 | `providerId/displayName`、支持分类、能力（如画质查询是否支持）；SDK 协议与身份由它自己的 Adapter 封装 |
| 作品引用 | `providerId + contentId`；跨 SDK 不能共用来源作品 ID，同名不同年/版本不能误合并 |
| 线路 | `providerId + contentId + lineCode`、显示名称、目录状态；大小写保留 |
| 剧集选择 | 稳定剧集身份、来源真实编号/名称、版本/季数匹配证据；不是页面数组下标 |
| 画质选项 | SDK 原始画质码、可展示名称、可选分辨率/编码信息、证据来源、平台可用性；不强迫未知 SDK 伪造画质 |
| 播放策略 | 自动最高画质或手动线路、预算、取消/代次；画质策略由公共会话负责，SDK 负责协议执行 |
| 已解析媒体 | 请求头、格式、过期时间、实际选择的提供方/线路/集数/画质及必要的说明；不能丢掉选择身份 |

`ContentSearchProvider` 已覆盖搜索/目录/解析，先对缺失能力做兼容性扩展，不为了未来接口创建大量空 Adapter。旧动漫规则不声明它没有实现的画质查询能力，本轮设计不改变那 16 条规则的行为。

`MioMediaService.play()` 可以向后兼容地新增可选画质参数，Python 桥已有入口能传给 SDK。清晰度比较需在桥接/会话层保留必要的候选证据；不要改动 SDK 的签名/加解密，也不把交换令牌、nonce、带凭证的 URL 暴露给 UI 或日志。

切换提供方、线路或集数必须递增播放代次并取消旧请求，最后一次明确选择生效。旧响应不能更新新选择的标题、画质、错误提示或播放器。

只有同一剧集且版本可匹配时才交接播放进度；不同剪辑/时间轴不能承诺精确续播。新媒体可用后再替换旧媒体，准备失败尽量保留原可播放会话，避免“点一下切线就清空画面”。

## 影响范围、实施切片与验收

实施时需要覆盖首页/搜索两种作品入口、统一来源注册、影视详情页面、播放会话、Python 封装和相关测试；只改“播放源”文字不能完成这个需求。Android 继续复用原生播放器，Web 使用现有控件，iOS 共用页面但仍需单独构建与运行验证。

建议按三个可独立验证的切片推进：

1. 来源分组与公共会话：外层 `miomedia`，内层动态线路，统一入口，保留已有起播能力。
2. 画质证据与自动策略：兼容性扩展画质参数，元数据并发、最高档优先、失败降级、预算与明确未知状态。
3. 换线续播与回归：当前集匹配/进度交接/手动锁定，未来 SDK 接入测试，三端播放器一致性验证。

验收至少包括：

- 片源区显示 `miomedia`，不把 7 种内部线路当成 7 个 SDK；无额外确认弹窗。
- 作品只有 1 条时显示 1 条，6 条时显示 6 条，新增合法第 8 种代码无需改页面白名单。
- 含 2160p 与 1080p 候选时优先可播放的 2160p，同档按成功与耗时选择；接口顺序颠倒不影响结果。
- 不把“蓝光超清+”或 `qualities[0]` 无条件当最高；未知画质不伪造数值；没有证据时如实展示。
- 手动换线直接匹配当前集并续播，旧请求迟到不覆盖；自动探测不覆盖手动选择。
- 失败/空目录/无对应集/不支持/总预算耗尽分别呈现；不会跳到别的电影、其他季或错误集数。
- 第二个不同线路编码/作品 ID/画质字段的测试 Adapter 能通过同一页面和会话工作，证明扩展点可用；产品列表不展示虚假已接入 SDK。
- Android 仍为原生播放器，Web 不重新创建不受控视频，既有搜索并发和首批结果展示不退化。

当前状态：研究 DONE；目标与拟议契约设计 DONE；应用实现为 NEXT。本轮没有修改播放代码，不把设计描述当成已实现。该改动建议在实施前以 OpenSpec 固定跨模块验收；本轮没有创建 OpenSpec 变更文件。
