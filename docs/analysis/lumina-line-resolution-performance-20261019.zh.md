# Lumina 线路解析等待分析

> 本文记录优化前的复现。后续已确认 Dart 原本就在调用 `calib_direct` 快路径，并补入同 K 缓存、空闲预加载和多画质材料复用；修订结论及新实测见 [优化验收](lumina-line-resolution-optimization-20261019.zh.md)。旧的 1,034 ms 不能作为“逐块 FFI 慢路径”的证据。

日期：2026-10-19。对象：当前 Dart + C 接入，C 引擎 `lumafuse-1.6`，雷电 Android 14、x86_64 应用；补充 Windows x64 同密文分段测试。本文不把旧 Python SDK 的性能当作当前 APK 的性能。

## 结论

**主要瓶颈是 C 引擎解密前的逐块标定。首页预加载与播放共用一个工作 isolate，进一步造成排队；同集切画质还会重复请求播放接口和解析器。** 去掉 Python 已完成运行链迁移，但并未消除引擎内部的转译解释执行成本。

当前播放路径为：页面匹配真实剧集 → 获取画质/播放材料 → `/app/video/play` → RSA 解信封密钥 → 推导 C(K) → `lumafuse_calib_direct` 逐块标定 → `lumafuse_decrypt` → 解析器 HTTP 请求 → AES/JSON 解包 → 打开媒体 → 视频首帧。

“线路解析完成”和“视频出首帧”是两个阶段。日志的 `video_first_frame` 从播放器打开媒体开始计时，不能当作点击到首帧的总耗时；要另加前面的等待和解析时间。

## 1. 雷电连续三次换集复现

测试使用正常 `main.dart` 的 release 诊断包，不是独立 smoke 页面。应用实际 ABI 为 x86_64。交替点击第 3、2、3 集，记录每轮日志，三次均复现播放响应解密超过 500 ms。此时没有进行 Flutter/Gradle 构建。

| 阶段 | 第一次 | 第二次 | 第三次 |
|---|---:|---:|---:|
| 播放接口 HTTP | 42.527 ms | 33.030 ms | 36.967 ms |
| 播放响应解密 | 1,288.052 ms | 1,615.226 ms | 1,621.252 ms |
| 解析器 HTTP | 583.585 ms | 550.897 ms | 595.577 ms |
| 解析器本地解包 | 0.029 ms | 0.030 ms | 0.034 ms |
| 上述播放解析阶段合计 | 1,914.193 ms | 2,199.183 ms | 2,253.830 ms |
| 打开媒体到首帧，另计 | 1,746 ms | 1,322 ms | 1,820 ms |

第一次另有详情缓存过期后的详情请求与解密，约 0.65 秒。此表仅为三个功能样本，不是 Android p50/p95，也不能用于比较新旧 SDK 提速比例。

证据保存在本地审计目录 `.dart_tool/lumina-reset-20261019-113222/line-repro.json` 和三份 `line-repro-*.log`。日志仅用于本地验收，未提交原始网络报文。

## 2. C 引擎内的时间花在哪里

[`LuminaEngine.decrypt`](../../packages/lumina_engine/lib/lumina_engine.dart) 每次先执行 `lumafuse_calib_direct(key, blockCount, constants, tweaks)`，再执行 `lumafuse_decrypt`。标定按整份密文长度运行，并非只完成一次普通 AES 解密。

SDK 自带 `sdk/python/bench_vs_app.md` 的结构说明与现有实现相符：便携 `_fuse` 保留转译解释器执行，标定需要运行镜像中的链式计算。采用 C 编写不等于已经拿到了可直接执行全部算法的独立高效 C 实现。

为区分标定与最终解密，在 Windows x64 对同一密文重复 20 次，首轮预热单列剔除；使用本次引入的同一 DLL，调用已核验的 C ABI，全部明文逐字节匹配。每种长度的密钥和密文固定，测试不包含 HTTP、RSA、JSON、Flutter 或 Android。

| 明文长度 | C(K) 推导 p50 / p95 | 逐块标定 p50 / p95 | 标定后 C 解密 p50 / p95 |
|---|---:|---:|---:|
| 256 B | 9.759 / 12.527 ms | 57.596 / 80.126 ms | 0.007 / 0.009 ms |
| 1,024 B | 10.608 / 11.874 ms | 242.734 / 258.322 ms | 0.022 / 0.023 ms |
| 4,096 B | 10.668 / 12.317 ms | 1,033.999 / 1,120.193 ms | 0.081 / 0.135 ms |

这些是 **Windows 合成输入的分段分位数**，不是 Android 业务耗时。它验证了瓶颈归属和随块数增长的趋势，不能把 1,034 ms 直接套在 Android 每条线路上。分段 p50 的相加也不等同于完整调用 p50。

本地可重跑脚本为 `.dart_tool/lumina-reset-20261019-113222/profile_native_stages.dart`，结果为 `native-stage-profile.json`。脚本使用私有镜像和 DLL，留在忽略目录，不进入 APP。重跑时从 `packages/lumina_engine` 的开发入口运行，使用该包依赖与 hook，避免触发整个应用的桌面插件编译。

## 3. 首页预加载确实阻塞了线路解析

重新启动诊断包，在主频道首次目录返回后立即进入作品。后台仍在依次预加载其他频道，实测：

| 阶段 | 耗时 |
|---|---:|
| 后台目录解密 | 2,156.445 ms |
| 详情请求进入 worker 前排队 | 1,733.860 ms |
| 随后一份后台目录解密 | 3,060.494 ms |
| 播放请求进入 worker 前排队 | 3,061.169 ms |
| 播放接口 HTTP | 35.259 ms |
| 播放响应解密 | 791.377 ms |
| 解析器 HTTP 阶段 | 1,678.493 ms |

两次显式排队累计已接近 4.8 秒。后一次解析器 HTTP 阶段还跨越了另一份 1,459 ms 的目录解密，因此它不能全算成服务器响应慢。

原因在 [`lumina_executor_io.dart`](../../lib/services/source/lumina/lumina_executor_io.dart)：一个长驻 isolate 接受异步请求，但其内部 FFI 调用同步完成。目录解密期间，已经返回的网络事件、后续请求和取消消息都要等待事件循环恢复。原生引擎使用进程全局状态，直接增加多个 isolate 并发调用同一 C 库会带来竞态，不能作为安全的直接修复。

[`LuminaHomeController`](../../lib/services/source/lumina/lumina_home_controller.dart) 当前主频道及预热窗口均为 12 条；首页首帧后会继续预热其他频道。串行预热只限制同时请求数量，没有赋予播放更高优先级。证据为 `line-preload-contention.json` 和同名日志。

## 4. 切换画质重复解析

同一集在约 9 秒内依次切换 1080p、自动，观察到两次完整的 `play → decrypt → parser`，分别解密约 946 / 830 ms。解析器网络分别约 642 / 1,621 ms；本地解包均不足 0.04 ms。

[`LuminaPlaybackProvider`](../../lib/services/source/lumina/lumina_playback_provider.dart) 的 `_qualities` 缓存 5 分钟，但它只保存画质描述；`_materials` 最多保留 27 秒，并在 `playEpisode` 中通过 `remove` 一次性消费。页面的 `PreparedPlayback` 又绑定单一画质，所以预解析已经消费后换档需要重新取整份结果，即使同一次解析原本就包含两个画质地址。

这是一项可以优化的取舍，并非密码算法算错。优化时必须保留短时凭证期限、作品/线路/真实集名身份隔离和媒体失败后的强制刷新；不能简单改成长期缓存直链。证据为 `line-quality-reparse.json` 和同名日志。

## 5. 建议的处理顺序

1. **先减少额外等待。** 将用户触发的 detail/play 与后台预加载分优先级；用户进入详情或发起播放时，停止派发后续预热任务。已经进入 C 的调用不能靠 Dart 取消立即中断。需在执行标定前再次判断优先级，单纯在 UI 取消旧 Future 不足以解决阻塞。
2. **在原短时窗口内复用同次解析的多画质材料。** 缓存键包含作品、线路与真实集名，切画质只选对应材料；不延长结果最初的有效期。提供显式强制刷新，媒体失效/重试立即淘汰缓存，避免一直重用坏地址。
3. **让目标线路先可用。** 当前自动准备会等待候选线路的画质探测；未来多线路响应变慢时，应先完成当前选择或首个符合 4K 策略的候选，再后台补齐其他候选。当前样本只有一条线路，这不是上述三次复现的主要瓶颈。
4. **解决计算成本需要引擎级交付。** 首选供应商提供跨端的直接响应解密 C ABI，避免每次按全密文运行转译镜像标定。需要正式头文件、内存/错误/线程契约和各端产物，尤其 iOS device/simulator XCFramework。现有未知导出符号不得猜签名使用。
5. **Android 可另做可选的进程内加速后端。** SDK 的 ARM64 官方 `libcore.so` 路径可用纯 C 适配调用，不要求 Python、adb 或常驻设备桥；但它只解决 Android ARM64，并有 JNI 环境、异步迟到回调隔离及 4 KiB LOAD 对齐问题。它不能代替跨端引擎或被宣称已支持 iOS/16 KiB 设备。雷电 ARM64 还包含 Houdini 翻译成本，仍应单独验收。

预计算表只覆盖已知密钥与有限块数，正常响应密钥未必命中；按密钥缓存标定也要先测真实复用率，不能据此承诺所有请求都变快。
