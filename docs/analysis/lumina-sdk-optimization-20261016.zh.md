# Lumina SDK 接入与优化分析

本报告依据提供的 SDK 实码、包内基准与 Playra 调用链，不修改供应商算法。版本事实以当前源码为准；包内历史测量不是本轮真机结果。

## 结论

优先减少重复网络和大响应，复用认证与引擎，再处理点击等待。密码链已具备原生加速和缓存，改算法、盲目增加线程或长缓存直链既不稳，也不符合本次约束。

| 优先级 | 优化项 | 实码依据 / 可验证收益 | 本轮边界 |
|---|---|---|---|
| P0 | 播放显式传真实 play_fmt、part | `client.py:173`任一缺省会先取detail；传齐可省一次详情往返及对应响应解密 | 接入层固定传原值，不重构part |
| P0 | 预解析与媒体打开分离 | URL解析是网络请求；准备时不得open/init，点击消费当前同身份结果 | 以状态机及媒体open计数验收 |
| P0 | 请求合并与取消 | 准备中点击、连续重建页面不能重复取凭证；旧generation结果不得落入新选择 | 单页面同集single-flight，换集取消，不预解析整部 |
| P0 | 原样携带headers | SDK空UA与Referer属于播放契约；原Web代理`||=`会覆盖空UA造成额外失败与重试 | 改为仅缺省时补UA，使用真实transport回归 |
| P1 | 每线程复用Client | `client.py:59–64`的90秒认证缓存是实例级；原`auth.py`仍为每请求生成nonce | 固定有界worker，thread-local Client，不共享可变Client |
| P1 | 首屏小分页、目录优先显示 | 响应越大，解包/解密/JSON/跨桥复制工作越多 | 首页目录与轮播独立返回，按需加载下一页；不一次拉全站 |
| P1 | 详情短缓存 | 准备目标集已有详情时，不应在多层Service重复请求相同内容 | 只缓存公开内容，取消结果不入缓存，直链独立短TTL |
| P1 | 引擎与镜像复用 | `_fuse`有内容哈希解压缓存、`_image_path`、`_lib`及进程级锁 | 保留实现；不能health探测时初始化，不能去锁 |
| P2 | 受控连接复用 | 原SDK`HTTPConnection`支持keep-alive；当前安全Adapter为每次请求建立并关闭连接，保留DNS固定、取消和响应限制 | 后续可单独验证线程内按host复用，未测量收益，不本轮盲目加入 |
| P2 | 有限预热与多进程 | 进程内引擎锁使堆线程无法增加解密并行；大吞吐才适合多进程 | 不为单用户APP启动额外进程；预热不得生成额外设备身份 |

## 哪些优化 SDK 已经做过

- 认证头缓存窗口90秒，nonce每请求变化。延长缓存或复用nonce不是有效接入优化。
- `block.py:310–318`的EBlock缓存属于实例；每个响应的随机密钥可能不同，不能宣称跨响应必然命中。
- `block.py:348–353`已有增量calibrate和direct路径，`block.py:453`已有原生批量解密。
- `_fuse`已缓存原生库与解压镜像，进程内RLock保护共享引擎。移除锁可能破坏正确性。
- 原SDK的Client本来复用HTTPConnection，不能笼统声称“标准库请求每次都新建TCP”。本轮宿主受限传输与原SDK传输的差异需要分别评价。

## 性能数据的正确用法

包内 `bench_vs_app.md` 记录相同密文、全冷解密的桌面历史数据：list约977ms、search约729ms、banners约449ms、config约251ms。这些数字不能直接当作 Android 阈值，也不能当作本轮实测。

现有 `bench_endpoints.py` 还存在包装签名漂移：其 `_timed_open(raw)` 为单参，而当前Client调用解包函数时传入raw、path两个参数。直接使用该脚本可能得到code为空/解密错误的无效测量。后续计时必须用外部兼容`*args/**kwargs`包装或仅在宿主操作边界计时，不为测速修改供应商算法。

建议分别记录：首次引擎/镜像准备、认证生成、API往返、响应解包、公共模型转换、外部解析器往返、媒体首帧、点击到首帧。每类同时报告冷/热、样本数、成功率及p50/p95；不要把准备URL成功当作实际解码成功。

## 缓存和身份红线

DEVICE_FP一次生成、私有持久复用，不能每次启动换设备；不缓存认证信封或source串到公共磁盘/报告。准备结果仅存当前页面内存，按SDK/作品/真实线路/真实part/画质区分，未知时效使用保守短TTL，点击时过期重取。真实媒体错误仍需保留；不会为了减少失败统计而隐藏错误。

`resolve=False`仍POST播放端点取凭证；缺省part/play_fmt时还会先取详情，分别为一次或两次接入点往返。它只跳过外部解析器，不能作为离线探活，也不满足“已准备可播放直链”。

## 平台优化边界

Windows x64、Linux x64/arm64、macOS arm64和Android arm64/x86_64可使用随包`_fuse`。ARM32不登记Lumina；按用户最新范围，iOS也不登记或展示Lumina，保留旧动漫来源，暂停远端/本地研究。`_native`在包内不存在，`_emu`依赖可选Unicorn且不满足本次零依赖约束，不为这两种无产物平台写降级实现。

Android原生库从只读JNI目录加载，镜像通过Chaquopy提取为真实数据文件，并解压至私有缓存；文件系统处理遵循 [Chaquopy Packaging](https://chaquo.com/chaquopy/doc/current/android.html#extractpackages)。实际项目插件为17.0，最终兼容性以本项目Gradle构建和设备验证为准，不因当前文档为17.1而升级依赖。

iOS脱离远端服务是另一项可行但尚未实施的迁移：Flutter支持Dart协议与本地C引擎，但当前SDK没有引擎源码/iOS产物。具体缺口、83.6MiB运行镜像、动态/静态链接区别与分阶段门禁见[iOS本地运行核验](lumina-ios-local-feasibility-20261016.zh.md)，不能把本轮远端配置当作本地引擎已接通。

## 本轮实际测量

桌面宿主真实小分页调用单次样本：config375ms、频道265ms、列表375ms、搜索328ms、详情1750ms、播放凭证及直链解析985ms；携带SDK请求头读取媒体前缀，HTTP200、video/mp4且包含ftyp签名。另一轮Range请求HTTP206。样本不构成p50/p95，网络与内容大小均影响耗时，不作为Android/iOS性能结论。

实际修复了两类会掩盖性能问题的正确性缺陷：SDK小写host与传输补充的Host重复导致上游HTTP400；Web媒体代理使用`||=`覆盖空UA。均以实际HTTP传输回归验证，不以mock返回成功代替请求头行为。内容审查另修复显式下拉刷新仍读五分钟缓存、Lumina慢请求串行阻塞其他首页内容刷新。
