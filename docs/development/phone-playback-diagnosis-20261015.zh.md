## 已确认原因与修改

### 资料目录被当作当前线路集数

`ModernPlayerDetailPage.loadEpisodeCatalog()` 读取 Bangumi 正片资料目录。未装入播放来源时，详情页用这份目录长度显示“共12集”；匹配真实来源后才切换成来源的2集。用户点击资料第3集时得到“暂未找到第3集的可用来源”，尚未进入媒体解析。

这不是 SDK 凭空返回了10集，也不能仅凭目录推断某集已播出。修复保留资料选集与真实分集身份，但在未匹配时明确显示“资料目录 / 目录12集”和“实际可播放集数以匹配来源为准”；取得来源后显示“选集 / 当前线路2集”。资料弹层也采用相同语义。没有按日期猜测可播放数量，没有删除目录记录。

### 首帧超时后错误无法恢复

`VideoPageController._resolveWithVideoSourceService()` 原生首帧预算为15秒。超时后 `_mediaFailure` 非空；迟到的首帧回调要求它必须为空，导致真实出画也无法标记成功、撤掉错误。异常出口又将 `MEDIA_ERROR` 包装为“视频解析失败”，混淆 SDK 解析和播放器阶段。

修改如下：

- 首帧预算统一为25秒，与现有 Web 动漫及 SDK 影视页相同，仍只累计前台有效启动时间。
- 仅当前 session + attempt 的首帧超时可在迟到出画后恢复；已取消、旧集、旧线路回调无权清理新状态。
- 真正的媒体错误会撤销超时恢复资格，即使之后到达帧回调也不清错。
- 成功结束加载时清理旧错误；恢复后正确标记当前集、当前线路，不取消手动锁定。
- 迟到起播同样执行既有真实时长校验，通过才恢复切源进度，时长不兼容时不 seek。
- 已取到地址后的媒体错误、首帧等待超时分别提示；不再统一声称 SDK 解析失败。

DM84 线路2桌面差分探针确认：媒体为约374 MB的 MP4，`moov` 位于尾部、约976 KB；Range 返回206且范围正确。这会增加启动所需请求，但桌面链路不能代表手机吞吐量，不能断言它是唯一根因。实际迟到出画足以排除“此地址必定不可播放”。本轮没有仅靠无限延长超时掩盖状态错误。
