## 外网 HLS 与解码

演示流为 `https://test-streams.mux.dev/x36xhzz/x36xhzz.m3u8`，未替换成本地视频。已经在嵌入画面和横屏全屏看到实际视频，暂停后显示“播放”，时间保持；进度条可以提交新的目标位置。跨全屏后 seek 的最终落点未取得充分证据，不列为通过。

这台设备的默认 `gpu` / `auto-safe` 实际选择 `mediacodec-copy`。缓存充足且速率约 5–6 MB/s 时仍明显掉帧，A/V 延迟增长，见 [基线采样](player-telemetry.json)。A/B 切换为 `mediacodec` 后，视频时钟每五秒推进约五秒，A/V 延迟接近零，首次三段采样零掉帧，见 [A/B 采样](gpu-mediacodec-telemetry.json)。

通过正式设置入口选择“性能优先”后，重新打开演示流再次确认实际使用 `mediacodec`，时钟 2 → 7 → 12 秒，五秒采样间隔，掉帧累计 1 → 3 → 5，见 [设置入口后的采样](final-external.json)。该结果支持明显改善，不能概括为所有片源和设备零掉帧。

默认仍为兼容优先，硬件解码关闭及已有自定义值保留。性能优先需要用户选择并重新打开视频；弹窗说明色彩取舍。[mpv 的 hwdec 文档](https://mpv.io/manual/stable/#options-hwdec)说明 MediaCodec 非复制路径可能影响色彩和高位深内容，因此没有全局强制切换。

## 真实剧集与网络限制

早期真实剧集已出画面并推进时间；后续重开第 01、02 集存在长时间缓冲。主播放列表及开始、120 秒附近分片的独立网络探测取得 HTTP 200，分片分别约 1.7 MB / 7.5 MB，耗时约 2.5 秒 / 1.3 秒，见 [网络探测](media-probe.json)。这些探测只能证明对应请求可达，不能证明真机持续播放稳定。

第 02 集在等待后开始推进，之后的真实历史记录显示 00:09 / 23:20（可见 320dp 首页截图），说明可以起播；这不足以证明持续播放和切集恢复稳定。
