# 冷启动图片、字体与栅格分析（2026-10-16）

## 范围与方法

L 级跨端性能修复，沿用已有 OpenSpec，完成 RESEARCH → DESIGN → IMPLEMENT → VERIFY → REVIEW。只处理图片加载/重绘和装饰图解码；不改首页 token、尺寸、字体、圆角、透明度、SDK 优先级、播放接口、历史收藏库或自定义规则。

区分三类证据：浏览器时间线用于归因，固定 22 秒浏览器采样用于复测；安卓使用 profile 的 Flutter FrameTiming，VM Embedder 时间线另作归因。归因采样的额外开销不能混进性能前后比较。冷启动指冷进程/新页面，保留设备原有应用数据及磁盘缓存，未执行卸载或清数据。

## 发现与处置

1. **图片变化会传播到外层绘制，但逐图加层不适合这次冷启动。** 诊断测试只标记内部 `RenderImage` 需要重画，外层装饰绘制计数从 1 增至 2；加边界后保持 1。然而安卓三轮整体栅格 P95 中位数由约 21.8ms 变为 27.5ms，未通过性能门禁。已撤回逐图边界及对应实验测试，不以减少一次 paint 作为整页更快的证明。
2. **Web 的缩略尺寸此前未真正执行。** 本项目锁定的 `cached_network_image_web 1.3.1`，默认 HtmlImage 分支直接返回 URL codec，不调用传入的 resize decoder。GPU 上传观察记录到小卡片仍使用宽 400/500/540px 的原图。复用同一个 OctoImage 淡入组件：原生继续 CachedNetworkImageProvider，Web 的 CachedBytesImageProvider 复用已有 CacheManager 的原始字节及并发请求，再执行各尺寸 decoder；解码错误交给框架 completer，并移除坏图的字节缓存。图片继续经已有同源 `/api/proxy`，未改变网关边界。
3. **装饰图的 1440px 解码宽度与显示大小无关。** 改为物理显示宽度向上取整，最少 1px，最大仍为既有 1440px。例如宽 180、DPR 2 时解码宽度由 1440 变为 360，3:1 图的像素数减少 93.75%；雷电首页背景宽 576、DPR 2 时目标为 1152，像素数减少 36%。这是解码像素预算，不是整页帧耗时改善百分比；Web 引擎仍可能先解压原图再缩小，不能宣称省去了全部原图解码。
4. **字体体积较大，但未证明裁剪能解决当前长帧。** 实测首次请求 MiSans 约 8.12MB，六套额外 Lucide 字重共约 2.93MB。受控屏蔽这六套字体后，首个 SDK 请求 1547 → 1648ms，浏览器非 idle 采样 3560 → 4144ms，未显示收益，故没有保留裁剪。单次实验与网络/主机噪声不能证明字体完全无成本；保留中文覆盖、正文与图标样式及系统字体设置。

安卓 VM 归因样本中：36 次图片解码分布于两个工作线程，合计约 132ms，单次最高约 46ms；纹理上传合计约 46ms，单次最高约 6.3ms。22 次着色器编译合计约 179ms；105 次栅格 Draw 合计约 1403ms，其中 SwapBuffers 约 976ms，包含呈现/驱动等待，不能全部解释为应用绘制运算。最长栅格 Draw 约 46ms；首次 UI layout 也有约 55ms 峰值。以上存在嵌套事件，不能把各项简单相加。

浏览器归因样本中，工作线程图片解码最高约 16ms，主线程图片解码最高约 12ms；单靠图片解码不足以解释所有启动长任务。JS/CanvasKit 初始化、首次文字排版和模拟器呈现等待仍是需分别看待的剩余成本，没有用“图片很大”代替完整结论。

## 实验记录

| 方案 | 结果 | 决定 |
| --- | --- | --- |
| 屏蔽未用 Lucide 字重字体 | 少约 2.93MB 请求，首屏/CPU 未改善 | 不保留，不裁剪字库 |
| 屏蔽网络封面 | 非 idle 采样 3560 → 3129ms，最大 RAF 未改善（167 → 200ms） | 仅归因实验，不移除图片 |
| 直接启用第三方 HttpGet | 缩略 decoder 可调用，但 HTTP 200 HTML 坏图实验产生 43 个 pageerror，图片等待未正常结束 | 不保留此分支 |
| OctoImage + Web NetworkImage | 输出缩略图，但不同尺寸使同一封面重复下载；两次观察 48 个代理资源请求，旧分支 31 个 | 撤回直接 NetworkImage，复用已有字节缓存 |
| 逐图重绘隔离 | 局部 paint 变少，安卓整体 P95 未改善 | 已撤回，避免额外合成层 |
| CachedBytesImageProvider、装饰图按密度解码 | 保持缓存及动效，执行缩略解码并正常收口错误；装饰图解码预算下降 | 实际两端验收后决定 |

## 追加问题：战狼2与查看更多

用户在同一轮追加了空线路截图和触底加载要求。真实接口复核：《战狼2》ID `318186661911851046` 的 `/video/detail` 返回 `player: []`，`currentEpisodes: 1` 只是资料字段；搜索返回同 ID、`hw8` 与 `tym3u8` 两条标记，但分别调用 `/resolve/episodes` 都得到空数组。这是来源目录缺失，尚未进入解析器，不是根据片名猜测，也不能把目录外的“1集”拼成可播放资源。未修改 SDK 算法或伪造线路。

“查看更多”另有两个入口：动漫弹层已有懒栅格和手动按钮，影视浏览页原来是 ListView 包裹 shrinkWrap 全量栅格。追加实施触底加载，并将影视页改为懒 SliverGrid，保持同一海报卡、列数、间距和既有手动操作。自动分页须区分纵向/向下滚动、请求中、已结束和失败暂停，不能由横向海报轨或失败后的每帧触发。

Web 实际操作已记录：影视查看更多通过鼠标滚动依次发出第 1、2、3 页请求，均为 20 条，分类 ID 始终一致；日漫精选弹层触底发出 Lumina 同频道第 2、3 页请求，均为 12 条，出现新增作品，均未点击手动加载按钮。初次测试发现默认返回按钮未退出 MaterialPageRoute，改为回到同一 Navigator，并新增返回回归。

完整 Flutter 回归 773 项通过；追加返回修复后的 6 项查看更多专项通过。受影响 9 个 Dart 文件及追加返回处的 analyzer 均无问题。Web 首页四张推荐的作品身份与边界在 1200×900 下与本轮开始时完全一致（x=240/605，y=122/284，355×152）。

最终安卓测量保留首个覆盖安装启动的异常样本：本机首 5 秒没有收到绘制帧，栅格峰值约 788ms；24 秒计时器的日志迟于脚本最初的 27 秒采集截止，已按同一 PID 补收，未丢弃或记作通过。它与普通冷进程重启分开报告，不能拿后续暖着色器数据掩盖首次安装峰值。后续脚本仅延长日志接收等待，不更改 24 秒帧收集计时或六次滚动时刻。
