## 已证实的原因

### 搜索、评价与讨论

本地 Android 构建原来未传入 `KAZUMI_APPID` / `KAZUMI_KEY`，而应用默认使用镜像。搜索和两类评论都属于镜像的签名保护接口。

实际以“吞噬星空”请求得到：

| 请求 | 实际结果 |
| --- | --- |
| 镜像作品搜索，空应用凭据 | `unauthorized: invalid request signature` |
| 官方作品搜索 | 200，共 9 个结果，包含作品 244239 |
| 镜像作品 244239 的评价 | 401，`invalid request signature` |
| 官方作品 244239 的评价 | 200，首批 20 条 |
| 镜像分集 992786 的讨论 | 401，`invalid request signature` |
| 官方分集 992786 的讨论 | 200，6 条 |
| 镜像作品 244239 的剧集目录 | 200，26 集 |

这些是 Windows 当前网络环境的真实 HTTP 样本；官方成功样本使用本机既有代理，并非安卓设备上的 ECH 验收。原始证据保存在 `.dart_tool/modern-load-diagnosis/`，部分初次请求超时，已与完整成功响应区分。

修复：没有完整凭据时，受保护请求直接走官方 API，原生复用 ECH，Web 复用浏览器传输；有签名但镜像返回 401/403 时，仅自动回退一次。普通镜像接口继续使用原设置。`officialOnly` 为请求级覆盖，不写入用户网络设置。构建脚本支持 `-DartDefineFromFile`，也会将 CI 同名环境变量通过临时文件传给 Flutter，结束时删除，避免密钥出现在命令参数或日志中。

### 四个主页面的加载

发现页原来等待完整目录才展示列表。目录包括两波资料请求、规则站点目录，以及最多 12 次补查；趋势和动画电影还使用普通 `apiDio` 绕过加速传输。每次重新进入页面 `force: true` 又绕过 5 分钟缓存。这与旧版单次榜单请求差异明显。

修复：首屏榜单与目录并行，先展示已到达的列表，分类资料完成后更新；动漫电影继续等待可靠分类，不用综合榜单冒充。目录缓存恢复，缓存身份包含来源版本、启用状态与加速方式。官方专用目录也经过统一 ECH/代理传输。

日历：当前季度主要接口与旧版相同；历史季度直连路径原来最多等待 10 页完整加载，仍是待优化路径。此次先让发现和日历离屏时暂停启动新的详情补查，日历离屏时也不因 App 恢复而刷新；已经在途的请求允许完成，不强制取消共享目录。

追番、我的：主体读取本地仓库，未发现等待 HTTP 的首屏阻塞。不能根据源码就断言与发现页同因。海报加载、手机上的构建/布局帧耗时仍需设备反馈；本次没有声称四页均已在设备上恢复速度。

## 新播放流程与边界

1. 进入详情页即请求作品资料的真实剧集目录，每 100 条逐页交付并显示正片分集，不等全部页完成。
2. 点击剧集或播放按钮，不弹选源窗口；按本地首帧速度/成功率统计优先调度，最多 4 个来源并发探测；首个确认同作品、同集且有非空播放目录的候选进入播放。
3. 选源总预算 30 秒，已有可靠缓存优先复用；得到候选或离开页面时取消剩余探测。没有匹配项时展示重试和手动换源入口。
4. 来源解析和首帧失败仍使用原播放会话的自动重试/换源（最多 3 个目标、原生总预算 120 秒，Web 180 秒）。不能把“最快返回目录”当成“本次所有源都测过首帧”；冷启动是按历史表现优先调度后的首个可用结果。
5. 使用正片集号匹配各来源真实路/集索引，保留季号和特别篇边界。无法证明匹配的候选不自动使用；资料目录代表作品集数，未表示每一集已经验证有资源。
6. 全部选集弹层先支持资料目录的分段、升降序、真实分集 ID；选源后继续用原线路和来源索引组件。显式手动换源保留核实步骤，可靠同集匹配时直接切换并检查进度恢复。
7. 历史来源核实成功仍恢复进度；无法核实时自动匹配同集，不把旧索引或进度猜配到新资源。离线入口继续使用原播放器流程。
8. 播放外壳安装来源后立即回调更新下方目录，不等待解析结束；人工打开换源后使旧自动任务失效，避免旧任务改变弹层状态。
9. 讨论可以使用已选资料分集的真实 ID；未开始播放也可手动选择讨论集数。不会把列表显示序号当成评论 API 的分集 ID。
